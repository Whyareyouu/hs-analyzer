# Graph Use Cases (Task 3.1)

## Цель

Зафиксировать конкретные аналитические задачи, где graph projection дает ценность поверх канонического match storage.

## 1. Поиск похожих позиций

### Сценарий

Найти historical позиции, похожие на текущий decision point:

- близкая конфигурация стола
- сопоставимый ресурсный профиль
- похожий тип доступных действий

### Почему граф

Граф позволяет сопоставлять позиции не только по плоским фичам, но и по структуре связей:

- сущность `Entity` в зоне
- источник эффекта `Action -> Outcome`
- цепочки событий в рамках хода

## 2. Причинно-следственный анализ `state -> action -> outcome`

### Сценарий

Для выбранного действия нужно восстановить:

1. контекст состояния до действия
2. само действие
3. ближайшие и отложенные последствия

### Почему граф

Естественная модель причинности выражается ребрами:

- `DecisionPoint -> Action`
- `Action -> Outcome`
- `Outcome -> Snapshot`

## 3. Explainability для рекомендации лучшего хода

### Сценарий

Нужно объяснить, почему рекомендация действия лучше альтернатив:

- какие паттерны прошлых матчей подтверждают выбор
- какие последствия чаще приводили к лучшему исходу

### Почему граф

Можно извлекать объяснимые цепочки:

- аналогичные decision points
- реальные executed actions
- связанные outcomes по близким позициям

## 4. Анализ цепочек эффектов, generated cards и переходов сущностей

### Сценарий

Разобрать сложные последовательности:

- триггеры, идущие каскадом
- генерация карт и их дальнейшая судьба
- переходы сущности между зонами

### Почему граф

Связи между событиями, сущностями и картами выражаются как path traversal, что проще и надежнее, чем ad-hoc SQL joins для длинных цепочек.

## 5. Query-level acceptance tests

Ниже - обязательный минимум запросов/проверок для приемки графового сценария.

### 5.1 Similar position lookup

- Given `decision_point_id`
- Query возвращает `top_k` похожих `DecisionPoint`
- Проверка:
  - все результаты принадлежат валидным матчам
  - similarity score детерминирован на фиксированном snapshot данных

### 5.2 Causal chain extraction

- Given `decision_point_id`
- Query возвращает цепочку `Snapshot(before) -> Action -> Outcome -> Snapshot(after)`
- Проверка:
  - цепочка не имеет разрывов ссылок
  - все узлы цепочки ссылаются на canonical IDs из primary storage

### 5.3 Explainability trace

- Given `decision_point_id` и `recommended_action`
- Query возвращает N исторических случаев с тем же типом действия и outcome-статистикой
- Проверка:
  - каждый случай имеет link на исходный `match_id/turn_id/event_id`
  - агрегация outcome повторяема при повторном запуске

### 5.4 Effect chain traversal

- Given `event_id` эффекта/триггера
- Query возвращает downstream chain событий и затронутых сущностей
- Проверка:
  - путь не содержит orphan узлов
  - для generated card доступна связь с событием генерации и последующими действиями

## 6. Критерий завершения 3.1

Шаг `3.1` считается завершенным, когда:

1. Зафиксированы ключевые сценарии (similarity, causality, explainability, effect chain).
2. Для каждого сценария определен query-level acceptance test.
3. Сценарии формализованы так, чтобы их можно было проверить после реализации projection слоя.
