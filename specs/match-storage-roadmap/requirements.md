# Requirements Document: Match Storage and Analysis Foundation

## Introduction

Подсистема `match-storage-roadmap` определяет новую основу хранения, реконструкции и аналитики матчей Hearthstone в проекте `hsanalyzer`. Цель подсистемы - заменить session-wide хранение тяжелых `timeline_*.json` на компактное каноническое хранение по одному матчу, сохранив возможность восстановить человекочитаемый лог, replay/debug представление и данные для будущего анализа игровых решений.

Новая подсистема должна отделять:

- каноническое хранилище фактов матча
- производные представления для человека
- аналитические проекции для будущего поиска лучшего хода

Корректно выполненные тесты являются обязательной основой приемки для всех требований этой подсистемы.

## Requirements

### Requirement 1: Единица хранения

**User Story:** Как разработчик анализатора, я хочу хранить каждый завершенный матч отдельной записью, чтобы не создавать один тяжелый JSON на всю игровую сессию.

#### Acceptance Criteria

1. WHEN система завершает обработку матча THEN она SHALL сохранять его как отдельную сущность хранения
2. WHEN в одной сессии обнаружено несколько завершенных матчей THEN система SHALL хранить их как независимые записи
3. WHEN запись матча сохранена THEN она SHALL иметь стабильный идентификатор `match_id`
4. WHEN пользователь запрашивает матч THEN система SHALL извлекать только данные этого матча без обязательной загрузки всей сессии

### Requirement 2: Каноническое хранение и source of truth

**User Story:** Как разработчик, я хочу, чтобы текущий тяжелый JSON перестал быть основным форматом хранения, чтобы система работала как на source-of-truth storage, так и на производных представлениях.

#### Acceptance Criteria

1. WHEN матч записан в новое хранилище THEN оно SHALL быть каноническим source of truth для фактов матча
2. WHEN требуется человекочитаемый лог или debug view THEN система SHALL строить их из канонического хранилища
3. WHEN старый `timeline_*.json` создается THEN он SHALL рассматриваться как производное представление, а не как первичное хранилище
4. WHEN схема канонического хранения изменяется THEN система SHALL поддерживать явное версионирование схемы

### Requirement 3: Scope новой подсистемы

**User Story:** Как разработчик, я хочу явно ограничить ответственность новой подсистемы, чтобы ingestion, хранение, материализация и аналитические проекции были четко разделены.

#### Acceptance Criteria

1. WHEN определяется scope подсистемы THEN он SHALL включать ingestion матчей, каноническое хранение, чтение, материализацию логов и аналитические проекции
2. WHEN определяется scope подсистемы THEN он SHALL не смешивать каноническое хранение с presentation-specific форматированием
3. WHEN реализуются компоненты подсистемы THEN их ответственности SHALL быть разделены на storage, materialization и projection layers
4. WHEN принимается архитектурное решение THEN оно SHALL быть зафиксировано в design document

### Requirement 4: Компактное дерево ходов

**User Story:** Как разработчик, я хочу хранить матч в компактной древовидной форме, чтобы быстро переходить к ходу и реконструировать его без дублирования полного state dump.

#### Acceptance Criteria

1. WHEN матч хранится в каноническом виде THEN система SHALL представлять его как `match -> turns -> event refs`
2. WHEN хранится узел хода THEN он SHALL содержать метаинформацию и ссылки, а не полный снапшот каждого объекта игры
3. WHEN требуется получить ход THEN система SHALL уметь восстановить его по дереву и связанным данным
4. WHEN сравнивается новый формат с текущим `timeline_*.json` THEN новый формат SHALL избегать многократного дублирования одинаковых карточных и state данных

### Requirement 5: Материализация читаемого лога

**User Story:** Как пользователь, я хочу по запросу получать полный понятный лог матча, чтобы компактное хранение не ухудшало читаемость и дебаг.

#### Acceptance Criteria

1. WHEN пользователь запрашивает человекочитаемый лог THEN система SHALL материализовать его из канонического хранения
2. WHEN пользователь запрашивает debug/replay представление THEN система SHALL материализовать его из канонического хранения
3. WHEN новый materialized output сравнивается со старым timeline output THEN система SHALL обеспечивать определенный критерий эквивалентности
4. WHEN запрашивается один конкретный ход THEN система SHALL уметь выдать его без материализации всех матчей сессии

### Requirement 6: Secondary projections и графовая аналитика

**User Story:** Как разработчик, я хочу иметь возможность строить графовые и другие аналитические проекции поверх канонического хранилища, чтобы не связывать первичный лог с конкретной аналитической моделью.

#### Acceptance Criteria

1. WHEN аналитическая проекция строится THEN она SHALL использовать каноническое хранилище как источник данных
2. WHEN графовая модель меняется THEN каноническое match storage SHALL оставаться стабильным source of truth
3. WHEN требуется rebuild аналитической проекции THEN система SHALL уметь перестроить ее из primary storage
4. WHEN графовая аналитика недоступна THEN каноническое хранение и материализация SHALL продолжать работать независимо

### Requirement 7: Foundation для анализа лучшего хода

**User Story:** Как разработчик аналитики, я хочу, чтобы новая модель хранения была пригодна для выделения decision points и анализа альтернативных действий, чтобы позже выявлять лучший ход в конкретной ситуации.

#### Acceptance Criteria

1. WHEN хранится матч THEN модель SHALL быть расширяема до `decision points`, `candidate actions` и `outcomes`
2. WHEN восстанавливается позиция хода THEN система SHALL иметь возможность получить достаточный контекст состояния для будущего анализа решений
3. WHEN анализируется действие игрока THEN система SHALL позволять связать выбранное действие с предшествующим состоянием и последующими событиями
4. WHEN скрытая информация не должна участвовать в честной оценке THEN архитектура SHALL допускать ее отделение от доступного игроку контекста

### Requirement 8: Тестируемость и приемка

**User Story:** Как владелец проекта, я хочу принимать реализацию новой подсистемы только по подтвержденным тестам, чтобы архитектурные решения не оставались на уровне деклараций.

#### Acceptance Criteria

1. WHEN реализуется любой пункт roadmap THEN для него SHALL быть определены соответствующие тесты
2. WHEN задача считается завершенной THEN ее тесты SHALL быть реализованы и успешно проходить
3. WHEN изменяется схема хранения, материализация или проекция THEN regression tests SHALL подтверждать отсутствие непреднамеренных изменений поведения
4. WHEN выполняется приемка этапа THEN критерием приемки SHALL быть успешное прохождение заранее определенного набора тестов
