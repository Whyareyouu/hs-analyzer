# Implementation Plan

## Правило приемки

- Для каждого пункта и подпункта implementation plan должны быть определены и реализованы соответствующие тесты.
- Корректно выполненные тесты являются обязательной основой приемки задачи.
- Задача не считается завершенной, если код реализован, но отсутствуют или не проходят тесты, подтверждающие ее поведение.
- Для каждого этапа необходимо заранее определить уровень проверки: unit, integration, regression, invariant/property или performance test.

- [x] 1. Сформировать архитектурное решение для нового слоя хранения матчей

  - Определить scope новой подсистемы: ingestion, хранение, материализация логов, аналитические проекции
  - Зафиксировать, что единицей хранения является один завершенный матч, а не session-wide `timeline_*.json`
  - Описать роли primary storage, secondary projections и debug/export форматов
  - Зафиксировать, что текущий толстый `timeline_*.json` становится производным представлением, а не source of truth
  - Подготовить acceptance tests для проверки соответствия архитектурных решений требованиям и ограничениям проекта
  - _Depends on: текущая архитектура analyzer/formatter/state_

- [ ] 2. Исследовать и выбрать primary storage для канонического хранения матчей

  - [ ] 2.1 Сформировать критерии выбора хранилища

    - Определить требования по размеру данных, скорости записи, скорости чтения одного матча и одного хода
    - Зафиксировать требования по локальному запуску без внешней инфраструктуры
    - Зафиксировать требования по миграциям схемы, дебагу, резервному копированию и переносимости
    - Определить требования к выборкам для будущего анализа решений
    - Подготовить тест-кейсы и benchmark-критерии для сравнения кандидатов на primary storage

  - [ ] 2.2 Сравнить кандидатов на primary storage

    - Сравнить `SQLite`, `PostgreSQL`, embedded key-value store, columnar/append-only варианты и файловое хранение
    - Оценить сложность интеграции каждого варианта в текущий Go-проект
    - Оценить удобство materialization полного лога и восстановления состояния на произвольном ходе
    - Выбрать рекомендуемое primary storage и зафиксировать причины выбора
    - Подтвердить выбор через воспроизводимые benchmarks, smoke tests и integration test criteria

  - [ ] 2.3 Зафиксировать стратегию source of truth

    - Зафиксировать, что все события, snapshots и decision points восстанавливаются из primary storage
    - Определить правила версионирования схемы и миграций
    - Определить формат идентификаторов `match_id`, `turn_id`, `event_id`, `snapshot_id`, `decision_point_id`
    - Определить regression tests для проверки корректности миграций и стабильности идентификаторов

- [ ] 3. Исследовать и выбрать графовую модель для аналитического слоя

  - [ ] 3.1 Определить задачи, ради которых нужен граф

    - Зафиксировать сценарии поиска похожих позиций
    - Зафиксировать сценарии причинно-следственного анализа `state -> action -> outcome`
    - Зафиксировать сценарии explainability для рекомендации лучшего хода
    - Зафиксировать сценарии анализа цепочек эффектов, генерации карт и переходов сущностей
    - Подготовить query-level acceptance tests для ключевых графовых сценариев

  - [ ] 3.2 Сравнить варианты graph storage

    - Сравнить полноценную graph DB, embedded graph-подходы и materialized graph поверх primary storage
    - Оценить стоимость поддержки, локального запуска и перестроения проекции
    - Выбрать, будет ли граф primary storage, secondary projection или optional analytics layer
    - Зафиксировать рекомендуемую стратегию интеграции графа с primary storage
    - Подготовить тест-критерии для rebuild graph projection и валидации целостности проекций

  - [ ] 3.3 Спроектировать минимальную graph schema

    - Определить узлы `Match`, `Turn`, `DecisionPoint`, `Snapshot`, `Action`, `Outcome`, `Entity`, `Card`
    - Определить связи между матчами, ходами, решениями, состояниями, действиями и последствиями
    - Зафиксировать минимальный набор свойств, достаточный для аналитики и explainability
    - Зафиксировать правила переиндексации графа из primary storage
    - Подготовить schema validation tests и query regression tests для графовой модели

- [ ] 4. Спроектировать компактную модель хранения одного матча

  - [ ] 4.1 Определить каноническую структуру матча

    - Спроектировать сущности `match`, `turn`, `event`, `entity`, `snapshot`, `decision_point`, `candidate_action`
    - Определить границы матча, правила завершения матча и правила записи неполных матчей
    - Зафиксировать обязательные и опциональные поля для каждого типа сущности
    - Зафиксировать schema versioning для match storage
    - Подготовить schema contract tests для чтения/записи структуры матча

  - [ ] 4.2 Спроектировать компактное дерево ходов

    - Зафиксировать дерево `match -> turns -> event refs` как навигационную структуру
    - Зафиксировать, что дерево хранит метаданные и ссылки, а не полный state dump на каждом узле
    - Описать, какие метаданные должны храниться в узле хода для быстрого доступа
    - Описать, какие данные должны выноситься в словари и отдельные таблицы/коллекции
    - Подготовить tests на корректность навигации по дереву и выборку одного хода без чтения всего матча

  - [ ] 4.3 Нормализовать карточные и сущностные данные

    - Вынести `card info` в отдельный словарь/справочник без многократного дублирования в событиях
    - Спроектировать словарь сущностей матча с историей привязки `entity_id -> card_id`
    - Определить, какие поля должны храниться inline в событии, а какие по ссылке
    - Зафиксировать стратегию хранения generated cards, discover options и скрытой информации
    - Подготовить tests на дедупликацию, разрешение ссылок и корректную обработку generated/hidden data

  - [ ] 4.4 Определить формат хранения событий

    - Зафиксировать event-sourced модель как основу реконструкции матча
    - Определить минимальный payload для `play`, `draw`, `attack`, `damage`, `heal`, `death`, `discover`, `effect_triggered`, `zone_change`
    - Спроектировать хранение timestamp, actor/target refs, зоны, ресурсов и источников эффектов
    - Описать правила backward-compatible расширения event schema
    - Подготовить unit и regression tests для всех базовых event payload contracts

- [ ] 5. Спроектировать snapshots и реконструкцию состояния

  - [ ] 5.1 Определить стратегию checkpoint/snapshot

    - Сравнить snapshots на каждом ходе, на decision points и только sparse checkpoints
    - Выбрать баланс между размером хранилища и скоростью реконструкции
    - Зафиксировать минимальный state snapshot, достаточный для анализа решений
    - Определить правила компрессии и дедупликации snapshot-данных
    - Подготовить tests на полноту snapshot-а, дедупликацию и корректность восстановления из checkpoint

  - [ ] 5.2 Спроектировать восстановление полного состояния

    - Описать алгоритм реконструкции состояния произвольного хода из snapshot + subsequent events
    - Зафиксировать требования к детерминированности replay
    - Определить требования к валидации reconstructed state против state analyzer-а
    - Зафиксировать стратегию диагностики рассинхронизации между event log и reconstructed state
    - Подготовить integration и invariant tests на детерминированную реконструкцию состояния

- [ ] 6. Спроектировать материализацию в человекочитаемый лог

  - [ ] 6.1 Определить контракт materializer/renderer

    - Спроектировать компонент, который собирает полный лог из compact storage по запросу
    - Зафиксировать режимы materialization: текстовый, human JSON, replay/debug JSON
    - Зафиксировать требования по latency для получения одного матча и одного хода
    - Определить контракты API между storage layer и formatter layer
    - Подготовить contract tests между storage reader и formatter/materializer

  - [ ] 6.2 Спроектировать реконструкцию текущего `timeline_*` формата

    - Описать, как из нового хранилища восстанавливается эквивалент текущему `human` timeline
    - Описать, как из нового хранилища восстанавливается эквивалент текущему `replay` timeline
    - Зафиксировать, какие поля могут стать optional/debug-only в materialized output
    - Определить критерии эквивалентности между старым и новым выводом
    - Подготовить regression tests на эквивалентность materialized output текущему timeline output

  - [ ] 6.3 Спроектировать точечный доступ к ходу и событию

    - Описать получение полного представления одного хода без материализации всего матча
    - Описать получение дерева хода, event list и reconstructed state для выбранного момента
    - Описать получение explainable view для будущего анализа решений
    - Подготовить integration tests на выборку одного хода, одного события и explainable view

- [ ] 7. Спроектировать модель decision points для анализа лучшего хода

  - [ ] 7.1 Определить, что считается decision point

    - Зафиксировать правила выделения момента принятия решения игроком
    - Определить, как фиксируются start-of-turn, post-draw, discover, attack sequencing и end-turn решения
    - Описать отличия decision point от обычного event node
    - Зафиксировать требования к идентификации decision points в логах
    - Подготовить tests на корректное выделение decision points в типовых игровых сценариях

  - [ ] 7.2 Спроектировать минимальный контекст решения

    - Зафиксировать обязательные признаки состояния: рука, стол, ресурсы, graveyard, известная информация об оппоненте
    - Определить, какие hidden/uncertain данные нельзя использовать в честной оценке лучшего хода
    - Описать хранение candidate actions и chosen action
    - Зафиксировать связи decision point с reconstructed snapshot и последующим outcome
    - Подготовить tests на полноту decision context и недопущение утечки скрытой информации

  - [ ] 7.3 Подготовить данные под будущую оценку лучшего хода

    - Определить, какие признаки должны быть извлекаемы для эвристик, ML и rule-based анализа
    - Зафиксировать требования к offline dataset generation
    - Описать, как сравнивать chosen action с альтернативными action candidates
    - Подготовить dataset validation tests и feature extraction regression tests

  - Определить unit-тесты для storage schema, writer, reader, materializer и replay reconstruction

  - Определить regression-тесты на эквивалентность старому timeline output
  - Определить property/invariant tests для согласованности `events`, `snapshots`, `turns` и `decision points`

  - Сравнить размер нового compact storage против текущего `timeline_*.json`
  - Сформировать целевые показатели по уменьшению размера и ускорению доступа

  - Этап 3: реализовать materializer для human-readable log и compatibility export
  - Этап 4: добавить snapshots и точечное восстановление хода
  - Этап 5: добавить decision points и candidate actions

  - Этап 7: подготовить foundation для анализа лучшего хода
