# Primary Storage Selection Criteria (Task 2.1)

## Цель

Зафиксировать воспроизводимые критерии выбора primary storage для канонического match storage, чтобы следующий шаг (`2.2`) сравнивал кандидатов по одинаковым измеримым правилам.

## 1. Требования к данным и операциям

### 1.1 Запись

- Операция записи: атомарная запись одного завершенного матча (`match + turns + events + metadata`).
- Требование: частичная запись матча не должна оставлять неконсистентное состояние source of truth.
- Требование: идемпотентность повторной записи одного `match_id`.

### 1.2 Чтение

- Критичные сценарии чтения:
  - чтение целого матча по `match_id`
  - чтение одного хода (`turn`) без загрузки всего матча
  - чтение диапазона событий внутри матча
- Требование: точечный доступ к ходу должен быть first-class сценарием, а не побочным эффектом full-scan.

### 1.3 Масштаб данных

- Хранилище должно эффективно работать с серией матчей без session-wide JSON.
- Минимальная целевая модель размера: рост данных линейный от числа матчей, без системного дублирования карточных метаданных на каждом событии.

## 2. Требования к локальному запуску

- Решение должно работать локально на Windows без обязательной внешней инфраструктуры.
- Базовый режим разработки и тестов должен запускаться одной командой (`go test ./...` + интеграционные тесты подсистемы).
- Разрешается optional внешний storage для расширенных сценариев, но primary путь разработки должен быть self-contained.

## 3. Миграции, дебаг, backup, переносимость

### 3.1 Миграции схемы

- Должно существовать явное версионирование схемы.
- Должна быть проверяемая стратегия forward migration.
- Обязателен regression-контур на совместимость чтения после миграций.

### 3.2 Дебаг

- Должен быть способ быстро инспектировать один матч и один ход без материализации всей истории.
- Должна быть воспроизводимая процедура диагностики расхождения `storage -> materialized output`.

### 3.3 Backup и переносимость

- Должна быть практичная стратегия резервного копирования локального хранилища.
- Должен быть понятный сценарий переноса между машинами/окружениями без ручного восстановления сложной инфраструктуры.

## 4. Требования к будущей аналитике решений

- Storage должен поддерживать выборки для будущих `decision points` и `state -> action -> outcome`.
- Хранилище должно позволять:
  - получить события матча в детерминированном порядке
  - связать событие с ходом и игроком
  - восстановить контекст конкретного decision момента
- Подготовка аналитических dataset должна быть возможна без чтения всех матчей в память одновременно.

## 5. Evaluation Matrix (для шага 2.2)

Каждый кандидат оценивается по шкале `0..5` и весам:

- Локальный запуск и простота эксплуатации: `20%`
- Транзакционная целостность и идемпотентность записи матча: `20%`
- Скорость чтения `match` и точечного чтения `turn`: `20%`
- Удобство миграций и versioning схемы: `15%`
- Дебаг/инспекция/backup/переносимость: `15%`
- Пригодность для аналитических выборок и projection rebuild: `10%`

Итоговый балл:

`score = Σ(weight_i * rating_i)`

## 6. Обязательные тест-кейсы сравнения кандидатов

### 6.1 Functional smoke

- Запись одного завершенного матча.
- Повторная запись того же `match_id` (идемпотентность).
- Чтение матча по `match_id`.
- Чтение одного `turn` без full materialization.

### 6.2 Migration regression

- Инициализация схемы `v1`.
- Миграция на `v2`.
- Чтение старых записей после миграции.

### 6.3 Recovery and consistency

- Имитация сбоя во время записи матча.
- Проверка, что после перезапуска нет полубитой канонической записи.

### 6.4 Projection readiness

- Построение вторичной проекции из primary storage.
- Повторный rebuild проекции после очистки projection-слоя.

## 7. Benchmark-критерии для шага 2.2

Сравнение кандидатов проводится на одинаковом dataset и одинаковом железе.

### 7.1 Write benchmarks

- `BenchmarkWriteMatchSmall` (короткий матч)
- `BenchmarkWriteMatchMedium`
- `BenchmarkWriteMatchLong` (длинный матч)

Метрики:

- p50/p95 latency записи матча
- throughput (matches/sec)

### 7.2 Read benchmarks

- `BenchmarkReadMatchByID`
- `BenchmarkReadTurnByMatchTurn`
- `BenchmarkReadEventRange`

Метрики:

- p50/p95 latency чтения
- объем I/O на операцию

### 7.3 Storage footprint

- Размер хранилища на 1, 100, 1000 матчей.
- Отношение размера к текущему `timeline_*.json` baseline.

### 7.4 Stability/soak

- Серия последовательных операций записи/чтения на длительном прогоне.
- Проверка отсутствия деградации и утечек ресурсов.

## 8. Критерий завершения шага 2.1

Шаг `2.1` считается завершенным, когда:

1. Зафиксированы измеримые критерии сравнения кандидатов.
2. Зафиксированы обязательные functional/regression/recovery тест-кейсы.
3. Зафиксированы benchmark-сценарии и метрики оценки.
4. Подготовлена scoring-модель для принятия решения на шаге `2.2`.
