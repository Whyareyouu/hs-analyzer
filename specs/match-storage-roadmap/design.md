# Design Document: Match Storage and Analysis Foundation

## Overview

Новая подсистема хранения матчей нужна для решения трех проблем текущего подхода:

- `timeline_*.json` хранит сразу несколько матчей в одном session-wide файле
- heavy JSON дублирует карточные данные, снапшоты состояния и вложенные структуры
- текущий output плохо масштабируется под будущий анализ решений и поиск лучшего хода

Базовая архитектурная идея:

- один завершенный матч = одна каноническая запись
- каноническое хранение содержит факты, а не presentation-ready dump
- человекочитаемые и debug представления строятся по запросу
- аналитические и графовые модели являются вторичными проекциями над primary storage

## Scope

Подсистема `match-storage-roadmap` покрывает:

- ingestion завершенного матча из текущего analyzer pipeline
- каноническое сохранение матча
- чтение матча и его частей
- материализацию в human/debug представления
- построение вторичных аналитических проекций

Подсистема не покрывает на этапе архитектурной фиксации:

- окончательный выбор конкретной СУБД
- реализацию ML/эвристики выбора лучшего хода
- финальную graph schema для всей аналитики

## Architectural Decisions

### 1. Единица хранения

Единицей хранения является **один завершенный матч**.

Это означает:

- session-wide `timeline_*.json` больше не рассматривается как канонический контейнер данных
- несколько матчей в логах должны распадаться на независимые записи
- все операции чтения и анализа строятся вокруг `match_id`

### 2. Source of Truth

Каноническое match storage является единственным source of truth для:

- матчей
- ходов
- событий
- снапшотов
- decision points

Все остальные представления являются производными:

- human-readable log
- compatibility JSON
- replay/debug JSON
- graph projection
- future analysis datasets

### 3. Разделение слоев

Архитектура делится на три роли:

#### Primary Storage Layer

Отвечает за:

- запись одного матча
- чтение одного матча
- стабильность схемы и идентификаторов
- восстановление исходных фактов матча

#### Materialization Layer

Отвечает за:

- сборку читаемого лога
- сборку compatibility output, аналогичного текущему `timeline_*`
- точечную выдачу одного хода или одной позиции

#### Projection Layer

Отвечает за:

- построение graph/analytics моделей
- выделение decision points
- будущий экспорт данных под эвристики и ML

Ключевое правило:

**projection layer не должен становиться каноническим хранилищем матча**.

## Canonical Match Model

На уровне архитектурного baseline каноническая модель должна включать:

- `match`
- `turn`
- `event`
- `entity`
- `snapshot`
- `decision_point`
- `candidate_action`

На первом этапе обязательными являются:

- `match`
- `turn`
- `event`

Остальные сущности фиксируются как обязательные расширения roadmap.

## Turn Tree

Навигационная структура матча строится как:

```text
Match
  -> Turn
     -> EventRef
     -> EventRef
  -> Turn
     -> EventRef
```

Это именно дерево навигации, а не полное хранилище содержимого.

В узле хода должны находиться:

- номер хода
- активный игрок
- временные метки
- счетчики событий
- ссылки на события
- ссылки на snapshot/decision points при необходимости

В узле хода не должны дублироваться:

- полные объекты карт
- полные объекты сущностей
- большие repeated snapshots на каждый event

## Event-Sourced Reconstruction

Матч должен восстанавливаться из:

- канонического event log
- редких snapshots/checkpoints
- словарей сущностей и карточных метаданных

Этот подход выбран потому что он:

- уменьшает размер хранения
- сохраняет детерминированность replay
- позволяет строить разные materialized views
- подходит для будущего анализа `state -> action -> outcome`

## Secondary Graph Projection

Графовая модель считается вторичной проекцией, а не первым источником истины.

Причины:

- primary storage должен быть проще для записи, миграций и дебага
- graph schema вероятно будет меняться по мере развития аналитики
- rebuild graph projection из стабильного source of truth дешевле, чем хранить весь матч только как граф

Таким образом допустимая целевая архитектура:

- `primary storage` для канонических данных матча
- `graph projection` для аналитики и explainability

## Debug and Export Policy

Текущий тяжелый `timeline_*.json` переводится в статус производного артефакта.

Допустимые производные режимы:

- compact canonical storage
- human-readable log
- compatibility JSON
- replay/debug JSON

Ключевое правило:

**ни один тяжелый export не должен быть единственным местом, где живут факты матча**.

## Testing and Acceptance

Для архитектурного baseline приемка строится через подтверждаемые артефакты и тестовые критерии.

Пункт 1 roadmap считается принятым, когда:

1. определен scope новой подсистемы
2. зафиксирована единица хранения `one match per record`
3. описаны роли primary storage, materialization и projection layers
4. зафиксировано, что `timeline_*.json` является производным представлением
5. описаны acceptance criteria, по которым эти решения можно проверять в последующих тестах

На следующих этапах каждое решение должно подтверждаться:

- unit tests
- integration tests
- regression tests
- invariant/property tests
- performance benchmarks

Без успешно пройденных тестов задача не считается принятой.
