# Implementation Plan

## Правило приемки

- Для каждого пункта и подпункта implementation plan должны быть определены и реализованы соответствующие тесты.
- Корректно выполненные тесты являются обязательной основой приемки задачи.
- Задача не считается завершенной, если код реализован, но отсутствуют или не проходят тесты, подтверждающие ее поведение.
- Для каждого этапа необходимо заранее определить уровень проверки: unit, integration, regression, invariant/property, soak или performance test.

- [x] 1. Сформировать архитектурное решение для live-monitoring режима

  - Определить scope новой подсистемы: поиск логов, long-running monitoring, detection active session, post-game persistence
  - Зафиксировать, что приложение должно поддерживать не только one-shot analyze, но и непрерывный режим работы
  - Описать взаимодействие live-monitoring режима с текущими `Analyzer`, `Parser`, `Pipeline` и будущим match storage
  - Зафиксировать, что после завершения матча результат должен сохраняться в каноническое хранилище матчей, а не только материализоваться в `timeline_*`
  - Подготовить acceptance tests для проверки соответствия архитектурных решений требованиям проекта
  - _Depends on: текущая архитектура analyzer/parser/logreader и roadmap `match-storage-roadmap`_

- [x] 2. Исследовать и выбрать стратегию запуска long-running процесса

  - [x] 2.1 Определить требования к runtime режиму

    - Зафиксировать требования к непрерывной работе процесса после запуска
    - Зафиксировать требования к graceful shutdown и восстановлению после перезапуска
    - Зафиксировать требования к использованию CPU, памяти и частоте polling/watch
    - Определить требования к диагностике статуса watcher-а и текущей активной сессии
    - Подготовить benchmark и soak-test criteria для runtime режима

  - [x] 2.2 Сравнить стратегии мониторинга файлов

    - Сравнить file system watch, polling, hybrid и tail-like стратегии чтения растущего `Power.log`
    - Оценить поведение при log rotation, truncate, recreate и задержках записи со стороны Hearthstone
    - Оценить переносимость решения для Windows как основной целевой платформы
    - Выбрать рекомендуемую стратегию мониторинга
    - Подготовить tests на корректность работы watcher-а в сценариях роста файла, ротации и повторного открытия

- [x] 3. Реализовать обнаружение путей к логам Hearthstone

  - [x] 3.1 Спроектировать стратегию поиска `Power.log`

    - Определить источники пути: явный CLI/config path, стандартные директории Hearthstone, auto-discovery
    - Зафиксировать приоритеты между конфигом, флагами и автообнаружением
    - Зафиксировать, что явный путь, переданный при запуске программы, является developer override и имеет максимальный приоритет
    - Зафиксировать правило, что `Power.log` является активным логом, а `Power_old.log` и другие `*_old.log` относятся к предыдущим клиентским сессиям
    - Описать поведение при нескольких найденных инсталляциях/каталогах
    - Подготовить tests на выбор корректного пути и fallback behavior

  - [x] 3.2 Реализовать поиск `Power.log` и связанных логов

    - Реализовать deterministic lookup для `Power.log`
    - Реализовать поиск соседних `Decks.log`, `LoadingScreen.log`, `LoadingScreen_old.log`, `Zone.log`
    - Исключить использование `Power_old.log` и других `*_old.log` как primary live stream активной сессии
    - Описать поведение при частичном наличии логов
    - Подготовить unit и integration tests для auto-discovery и partial availability

  - [x] 3.3 Интегрировать поиск логов с конфигурацией и CLI

    - Добавить режимы `auto`, `explicit path`, `mixed fallback`
    - Зафиксировать, что неверный explicit path приводит к явной ошибке, а не к тихому переключению на auto-discovery
    - Зафиксировать сообщения об ошибках и диагностический вывод при невозможности найти логи
    - Подготовить CLI/config regression tests

- [x] 4. Спроектировать и реализовать live reader для растущего `Power.log`

  - [x] 4.1 Определить контракт live log reader

    - Спроектировать интерфейс для чтения новых строк по мере роста файла
    - Определить поведение при достижении EOF и ожидании новых данных
    - Определить поведение при truncate/recreate файла
    - Подготовить contract tests для live reader

  - [x] 4.2 Реализовать incremental reading

    - Реализовать чтение только новых данных, а не всего файла при каждом обновлении
    - Реализовать сохранение offset/state для текущей сессии процесса
    - Описать поведение при неполных строках, буферизации и burst записи
    - Подготовить unit и integration tests на incremental reading

  - [x] 4.3 Реализовать устойчивость к проблемам лог-файла

    - Обработать truncate, file replace, временное отсутствие файла и задержки записи
    - Обработать временные I/O ошибки без падения процесса
    - Подготовить fault-tolerance tests и soak tests

- [ ] 5. Спроектировать и реализовать определение активной игровой сессии

  - [ ] 5.1 Зафиксировать модель active session

    - Определить, что считается активной сессией и когда она начинается
    - Определить, как различать отсутствие игры, поиск матча, активный матч и завершенный матч
    - Описать жизненный цикл сессии и переходы состояний
    - Подготовить state-transition tests для модели active session

  - [ ] 5.2 Реализовать session detection по входящим событиям

    - Использовать `Power.log` и связанные логи для определения начала и конца матча
    - Зафиксировать критерии завершения матча, даже если полный `GameEndEvent` не всегда приходит идеально
    - Реализовать буфер текущей активной сессии
    - Подготовить integration tests для начала, продолжения и завершения сессии

  - [ ] 5.3 Обработать edge cases сессий

    - Обработать незавершенный матч при падении приложения
    - Обработать перезапуск Hearthstone во время наблюдения
    - Обработать сценарий, когда предыдущая клиентская сессия уходит в `*_old.log`, а активная продолжается в новом `Power.log`
    - Обработать несколько матчей подряд без перезапуска мониторинга
    - Подготовить regression tests для crash-recovery и multi-game scenarios

- [ ] 6. Спроектировать post-game pipeline

  - [ ] 6.1 Определить момент финализации матча

    - Зафиксировать, в какой момент активная сессия считается достаточно полной для записи
    - Зафиксировать правила debounce/finalization, чтобы не сохранять матч дважды
    - Подготовить tests на корректную одноразовую финализацию

  - [ ] 6.2 Интегрировать live session с analyzer pipeline

    - Определить, как live-накопление событий переиспользует существующий analyzer/pipeline
    - Зафиксировать, когда матч преобразуется в `state.State` / match aggregate перед сохранением
    - Подготовить integration tests на связку `live reader -> parser -> analyzer -> finalize`

  - [ ] 6.3 Интегрировать сохранение матча в БД

    - Зафиксировать контракт записи завершенного матча в каноническое match storage
    - Определить поведение, если storage временно недоступен
    - Описать retry/idempotency стратегию
    - Подготовить tests на успешную запись, retry и защиту от duplicate save

- [ ] 7. Спроектировать и реализовать режимы запуска CLI

  - [ ] 7.1 Определить CLI/command model

    - Выбрать, будет ли это новый subcommand, режим `analyze --watch` или отдельный daemon-like command
    - Зафиксировать флаги для auto-discovery, verbose status, output policy и storage behavior
    - Подготовить acceptance tests для CLI surface

  - [ ] 7.2 Реализовать live-monitoring команду

    - Добавить команду/режим для постоянного наблюдения за логами Hearthstone
    - Добавить статусный вывод: найденные логи, активная сессия, завершение матча, результат записи
    - Подготовить command integration tests

  - [ ] 7.3 Реализовать graceful shutdown

    - Обработать `Ctrl+C` и штатное завершение процесса
    - Зафиксировать, что незавершенная сессия либо сохраняется как incomplete, либо откатывается по правилам проекта
    - Подготовить shutdown tests

- [ ] 8. Спроектировать observability для live режима

  - [ ] 8.1 Определить logging и status model

    - Определить обязательные structured logs для watcher-а, session detector и persistence pipeline
    - Определить пользовательский статусный вывод для long-running режима
    - Подготовить tests на наличие ключевых диагностических сообщений

  - [ ] 8.2 Определить health и self-diagnostics

    - Зафиксировать признаки “watcher healthy”, “log path missing”, “session active”, “storage degraded”
    - Описать минимальный self-check flow
    - Подготовить tests на health state transitions

- [ ] 9. Подготовить стратегию отказоустойчивости и восстановления

  - Описать поведение при временном исчезновении `Power.log`
  - Описать поведение при перезапуске Hearthstone
  - Описать поведение при появлении/сохранении `Power_old.log` и других `*_old.log` рядом с активными файлами
  - Описать поведение при падении самого monitor процесса
  - Описать стратегию восстановления offsets, active session state и pending persistence
  - Подготовить recovery tests и long-running soak tests

- [ ] 10. Подготовить стратегию тестирования live-monitoring подсистемы

  - Определить unit-тесты для path discovery, watcher, session detector и finalizer
  - Определить integration-тесты для полного цикла `log append -> session detect -> match finalize -> persist`
  - Определить regression-тесты на сценарии truncate/recreate/restart
  - Определить soak-тесты на длительное наблюдение и серию последовательных матчей
  - Зафиксировать, что прохождение этого набора тестов является обязательным gate для приемки каждой завершенной реализации

- [ ] 11. Подготовить стратегию производительности для live режима

  - Определить допустимые пределы CPU, памяти и задержки обработки новых строк
  - Определить допустимую задержку между завершением матча и записью в БД
  - Сформировать performance acceptance criteria для long-running режима
  - Подготовить benchmark tests

- [ ] 12. Подготовить поэтапный план реализации

  - Этап 1: архитектурно зафиксировать live-monitoring режим и его связь с match storage
  - Этап 2: реализовать auto-discovery логов и live reader для `Power.log`
  - Этап 3: реализовать session detector и finalization pipeline
  - Этап 4: интегрировать сохранение каждого завершенного матча в БД
  - Этап 5: добавить CLI режим постоянного наблюдения и graceful shutdown
  - Этап 6: закрыть observability, recovery и soak/performance acceptance
  - Для каждого этапа определить обязательный набор тестов и зафиксировать, что этап не принимается без их успешного прохождения
