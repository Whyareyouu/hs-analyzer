# Архитектура

## Базовый поток данных

Проект устроен как последовательность:

1. `logreader` читает файлы построчно
2. `parser` превращает строки логов в доменные `game.Event`
3. `analyzer` объединяет события из разных логов
4. `pipeline` применяет события к `state.State`
5. `formatter` строит человекочитаемый или JSON-вывод
6. `cmd/hsanalyzer` связывает все через CLI

## Что важно не ломать

- Новая логика парсинга должна добавляться в соответствующий parser, а не в formatter или CLI.
- Formatter не должен парсить лог-строки.
- CLI не должен содержать предметную логику Hearthstone.
- `state.State` остается центральной моделью итогового состояния игры.
- Если событию нужны человекочитаемые fallback-данные, их лучше протаскивать из parser в `game.Event`, а не надеяться только на итоговое состояние.

## Регистрация компонентов

- Парсеры регистрируются через `parser.Registry`.
- Форматтеры регистрируются через `formatter.Registry`.
- В `cmd/hsanalyzer/container.go` используется dependency injection через сборку контейнера.

## Расширение системы

- Новый лог-файл: добавить parser + регистрацию в container + тесты на реальных логах.
- Новый тип события: добавить `game.Event`, поддержку `Apply`, formatter-тесты и parser-тесты.
- Новый формат вывода: отдельный formatter, не через разрастание существующего `TextFormatter`.
